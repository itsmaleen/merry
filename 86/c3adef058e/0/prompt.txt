## Finding 1: Silent Re-Pairing via Deep-Link / QR Code — No Confirmation UI

**File:** `ios/cmux/App/AppState.swift:75–89` and `ios/cmux/App/cmuxApp.swift:19–21`

**Severity:** High
**Category:** Authentication bypass / credential hijacking
**Confidence:** 0.95

**Code excerpt:**
```swift
// cmuxApp.swift:19-21
.onOpenURL { url in
    appState.handlePairingURL(url)
}

// AppState.swift:75-89
func handlePairingURL(_ url: URL) {
    guard url.scheme == "cmux-bridge",
          url.host == "pair",
          ...
    let credentials = PairingCredentials(host: host, port: port, token: token, tailscaleHost: tailscaleHost)
    try? pairingStore.save(credentials)   // immediately overwrites Keychain
    connect(to: credentials)              // connects to attacker's host
    isPairingPresented = false
}
```

**Description:** Any `cmux-bridge://pair?host=...&amp;port=...&amp;token=...` URL that reaches the app — whether from a malicious QR code, a web page, an iMessage link, an AirDrop file, or another installed app — immediately and silently: (1) overwrites the stored bearer token in Keychain, (2) establishes a WebSocket connection to the attacker-controlled host, and (3) dismisses the pairing screen. The victim receives zero confirmation dialog, zero display of the new host, and no way to compare the incoming credentials against the existing pairing before they are committed. The `PairingView.swift` QR scanner path calls the same `handlePairingURL` with no interstitial either (line 51–52).

**Exploit Scenario:** An attacker running a server on LAN (or even a public IP) generates a valid-looking QR code or a URL of the form `cmux-bridge://pair?host=attacker.lan&amp;port=47821&amp;token=any`. They print this on a poster near the target's desk, send it in a message, embed it on a web page, or display it on a second screen. The victim's phone camera (iOS Universal Links) or any URL-opening action silently re-pairs the app. All subsequent keystrokes, terminal content reads, and `surface.send_text` calls now go to the attacker's host. The attacker also receives a new (attacker-chosen) bearer token which their server accepts.

**Fix:** Add a confirmation alert before committing the new credentials:
```swift
func handlePairingURL(_ url: URL) {
    // ... parse ...
    // If already paired, show UIAlertController / SwiftUI Alert:
    // "Pair with &lt;host&gt;:&lt;port&gt;? This will replace your current pairing."
    // Only on explicit confirmation:
    try? pairingStore.save(credentials)
    connect(to: credentials)
}
```
Also display the parsed host and port in the alert so the user can verify they match their Mac. Consider additionally checking that the new host is reachable on the local network before overwriting stored credentials.

## Finding 2: Cleartext WebSocket (ws://) Sends Bearer Token and All Terminal Content in the Clear

**File:** `ios/cmux/Connection/BridgeClient.swift:124–128`

**Severity:** High
**Category:** Credential and data exposure / missing transport encryption
**Confidence:** 0.95

**Code excerpt:**
```swift
let urlString = "ws://\(host):\(credentials.port)/ws"
guard let url = URL(string: urlString) else { return }

var request = URLRequest(url: url)
request.setValue("Bearer \(credentials.token)", forHTTPHeaderField: "Authorization")
```

**Description:** The connection is always `ws://` (cleartext). The bearer token is transmitted in an HTTP `Authorization` header during the WebSocket upgrade handshake, and subsequently every command sent to the bridge — including `surface.send_text` carrying keystrokes, passwords, and arbitrary terminal input — travels in plaintext. The Info.plist has no `NSAppTransportSecurity` block at all, which means ATS applies to HTTPS/TLS connections but is simply not relevant here because `URLSessionWebSocketTask` with a `ws://` URL bypasses ATS entirely (ATS governs HTTP/HTTPS; `ws://` is a native WebSocket and ATS does not block it).

**Exploit Scenario:** Any device on the same LAN segment (coffee shop Wi-Fi, shared office network, a compromised router) can passively capture the WebSocket upgrade frame and read the `Authorization: Bearer &lt;token&gt;` header in cleartext. With the token an attacker can connect to the bridge from any host on the network and issue arbitrary terminal commands. Additionally, all terminal output (surfaced via `surface.read_text`) flows back over the same cleartext channel, leaking every password typed, private keys displayed with `cat`, and command output.

**Fix:** Switch to `wss://` and provision a TLS certificate on the bridge (`cmux-bridge`). For a LAN/local tool where a CA-signed cert is impractical, use a self-signed certificate with certificate pinning: generate a keypair on first bridge launch, embed the public key fingerprint in the QR code / pairing URL, and verify it in the iOS `URLSessionDelegate`:

```swift
// AppState.swift / BridgeClient.swift
let urlString = "wss://\(host):\(credentials.port)/ws"
// In URLSession(_:didReceive:completionHandler:), pin against stored fingerprint
```

At minimum, document the plaintext risk clearly and add a UI warning when connecting over a non-localhost address.

## Finding 3: mDNS Auto-Reconnect Trusts Discovered Host Without Token Verification

**File:** `ios/cmux/Connection/BridgeDiscovery.swift:44–58` and `ios/cmux/App/AppState.swift:566–573`

**Severity:** Medium
**Category:** Authentication bypass
**Confidence:** 0.85

**Code excerpt:**
```swift
// AppState.swift:566-573
func discovery(_ discovery: BridgeDiscovery, didFind candidates: [PairingCredentials]) {
    guard connectionStatus == .disconnected,
          let stored = try? pairingStore.load() else { return }
    if let match = candidates.first(where: { $0.host == stored.host &amp;&amp; $0.port == stored.port }) {
        connect(to: PairingCredentials(host: match.host, port: match.port,
                                       token: stored.token, ...))
    }
}

// BridgeDiscovery.swift:52-54 — candidates are built with token: ""
return PairingCredentials(host: cleanHost, port: svc.port, token: "")
```

**Description:** `BridgeDiscovery` listens for `_cmux-bridge._tcp.` mDNS advertisements and auto-reconnects when the app is disconnected by matching only on `host` and `port`. An attacker on the LAN can advertise the same mDNS service name with the legitimate host's hostname and port. Because mDNS is unauthenticated on local networks, the comparison `$0.host == stored.host &amp;&amp; $0.port == stored.port` can be satisfied by a spoofed advertisement pointing to the attacker's IP. The stored token is then sent to the attacker's WebSocket server in the Authorization header.

**Exploit Scenario:** Attacker joins the same Wi-Fi and broadcasts `_cmux-bridge._tcp.` with the victim's hostname (or spoofs mDNS responses for that hostname). When the app is disconnected and reconnects, it sends the stored bearer token to the attacker's server and begins forwarding keystrokes.

**Fix:** The matching should additionally verify the resolved IP address matches what was originally paired (store the paired IP alongside the hostname), or rely solely on the token for authenticating the bridge: the connection attempt will fail with an auth error if the token is wrong, but the token is still transmitted in the clear over the unencrypted channel (which ties back to Finding 2). The real fix is wss:// with certificate pinning so that a rogue server cannot receive the token.

**Key findings:**

1. **URLSession retain cycle** — `startConnection` creates a new `URLSession` with `delegate: self` (the `BridgeClient`). `URLSession` strongly retains its delegate. Over many reconnects this leaks.

2. **`currentSection` crash** — `QuickActionState.currentSection` falls back to `sectionOrder[0]` when the index is out of bounds. If `sectionOrder` is empty (all built-in sections hidden AND no custom actions), this crashes. Same for the `open(with:)` accessing `sectionOrder[0]`.

### BUG 2 — HIGH: URLSession leaks `BridgeClient` on every reconnect

**File:** `ios/cmux/Connection/BridgeClient.swift`, line 131

```swift
let session = URLSession(configuration: .default, delegate: self, delegateQueue: nil)
self.session = session
```

**Severity:** High (retain cycle / memory leak)

**Trigger:** Every reconnect attempt. `URLSession` strongly retains its delegate (documented behavior — Apple explicitly warns about this in `URLSession.init(configuration:delegate:delegateQueue:)`). When `self.session` is reassigned, the old session is released from the Swift side but the session itself still has internal pending operations and continues to strongly hold `BridgeClient`. The old session is never `invalidate()`d so it never releases the delegate reference. After N reconnect cycles, N-1 old sessions are each strongly retaining `BridgeClient`, creating a retention chain that prevents deallocation.

**Fix:** Invalidate the old session before replacing it:
```swift
private func startConnection() {
    self.session?.invalidateAndCancel()   // releases delegate reference
    ...
    let session = URLSession(configuration: .default, delegate: self, delegateQueue: nil)
    self.session = session
    ...
}
```
Also call `self.session?.invalidateAndCancel()` in `disconnect()`.

### BUG 3 — HIGH: `handleDisconnect` called twice on clean server close (double reconnect scheduled)

**File:** `ios/cmux/Connection/BridgeClient.swift`, lines 147 and 272

```swift
// In receiveNext():
case .failure:
    self.handleDisconnect(error: nil)

// In URLSessionWebSocketDelegate:
func urlSession(_ session:..., didCloseWith closeCode:..., reason:...) {
    handleDisconnect(error: nil)
}
```

**Severity:** High (state machine bug)

**Trigger:** When the server sends a proper WebSocket close frame (normal, going-away, etc.), the receive callback fires `.failure` (the task is cancelled/closed) AND `didCloseWith` fires. Both call `handleDisconnect`. This results in:
- `clientDidDisconnect` delivered twice to `AppState` (two `connectionStatus = .reconnecting` assignments — harmless in isolation, but indicates double delivery)
- `scheduleReconnect()` called twice: two `reconnectTask`s are created, the second overwrites the first (so the first becomes uncancellable via `reconnectTask?.cancel()`), and at the scheduled time, `startConnection()` is called twice in parallel, creating two concurrent WebSocket connections

**Fix:** Add a `isDisconnecting` flag or check whether `task == nil` before proceeding:
```swift
private func handleDisconnect(error: Error?) {
    guard task != nil else { return }   // already handled
    task = nil
    ...
}
```
Since `receiveNext` and the delegate callback race on the URLSession internal queue (not the main thread), use the existing `completionsLock` or a dedicated flag protected by it to make the guard atomic.

### BUG 5 — MEDIUM: `cycleSurfaceBackward` inconsistent fallback when no surface focused

**File:** `ios/cmux/App/AppState.swift`, lines 167–173

```swift
func cycleSurfaceBackward() {
    let list = surfaces
    guard !list.isEmpty else { return }
    let currentIndex = list.firstIndex(where: { $0.id == focusedSurfaceID }) ?? 0  // &lt;-- fallback 0
    let prevIndex = (currentIndex - 1 + list.count) % list.count
    focusSurface(list[prevIndex].id)
}
```

Compare with `cycleSurface()` which falls back to `?? -1`, making "forward from nothing" go to index 0. `cycleSurfaceBackward` uses `?? 0`, making "backward from nothing" go to index `count - 1` (the last surface). These are asymmetric in a way that's confusing: volume-down cycles forward to surface 0, then if nothing is focused yet (e.g. right after reconnect), volume-down-backward cycles to the last surface instead of staying at 0.

**Severity:** Medium (UX logic error)

**Fix:** Use `?? -1` and add `list.count` so modulo stays positive, as `cycleSurface` does:
```swift
let currentIndex = list.firstIndex(where: { $0.id == focusedSurfaceID }) ?? -1
let prevIndex = (currentIndex - 1 + list.count) % list.count
```
When `currentIndex == -1`: `(-1 - 1 + count) % count = (count - 2) % count` — wraps to second-to-last? Actually for `count == 1`, that gives `0 % 1 = 0` (correct). For `count == 2`, `(-1 - 1 + 2) % 2 = 0 % 2 = 0` — backward from nothing goes to 0, which is symmetric with forward. For `count == 3`, `(-1 - 1 + 3) % 3 = 1 % 3 = 1` — backward from nothing goes to 1, forward goes to 0. That's reasonable and consistent. The key is both functions agree on "no current" behavior.

### FINDING 1 — Cleartext WebSocket transmits the bearer token over the wire (HIGH)

**File:line:** `bridge/internal/ws/auth.go:14-16`, `bridge/cmd/cmux-bridge/main.go:287-288`

```go
auth = "Bearer " + r.URL.Query().Get("token")   // token in query param, plaintext
// ...
addr := fmt.Sprintf(":%d", cfg.BridgePort)      // ":47821" = 0.0.0.0, no TLS
```

**Severity:** High

**Attack scenario:** The bridge serves `ws://` only — there is no TLS anywhere in the codebase. When the iOS app connects over LAN (not Tailscale), the full WebSocket upgrade request — including the bearer token in the `Authorization` header or `?token=` query parameter — is transmitted in cleartext. Any host on the same LAN/Wi-Fi segment can capture it with a passive ARP spoof or promiscuous mode capture. Once the token is captured, the attacker has full persistent access to the bridge (the token never rotates). The QR URL also contains the token (`cmux-bridge://pair?...&amp;token=TOKEN`) as plaintext on screen — shoulder-surfable and would be in any screen recording.

**Recommended fix:**
Add mutual TLS. Generate a self-signed CA + server cert on first run, store in `~/.config/cmux-bridge/`, embed the certificate fingerprint in the QR URL so the iOS app can pin it. Alternatively, use the Tailscale path (which does provide encryption) and make it the strongly-recommended mode for users on untrusted networks. At minimum, add a startup warning when Tailscale is not enabled.

### FINDING 2 — Token comparison is not constant-time (LOW-MEDIUM)

**File:line:** `bridge/internal/ws/auth.go:21`

```go
return provided == token &amp;&amp; provided != ""
```

**Severity:** Low-Medium

**Attack scenario:** Go's `==` on strings is not guaranteed constant-time; it short-circuits on the first differing byte. Over a local TCP connection the timing oracle is extremely noisy (millisecond-scale network jitter dwarfs byte-comparison time), so a remote LAN attacker needs millions of attempts to extract signal. This is a low-probability attack but it is real against a high-value target with LAN access and no rate limiting (see Finding 4).

**Recommended fix:**
```go
import "crypto/subtle"
return provided != "" &amp;&amp; subtle.ConstantTimeCompare([]byte(provided), []byte(token)) == 1
```

### FINDING 3 — No HTTP server read timeouts; vulnerable to Slowloris-style connection exhaustion (MEDIUM)

**File:line:** `bridge/internal/ws/server.go:39`

```go
s.httpServer = &amp;http.Server{Handler: mux}
```

**Severity:** Medium

**Attack scenario:** The `http.Server` has no `ReadHeaderTimeout`, `ReadTimeout`, or `WriteTimeout` set. An unauthenticated attacker on the LAN can open TCP connections to port 47821 and send partial HTTP headers very slowly, keeping each connection open indefinitely. Go's default `http.Server` allocates a goroutine per connection. With enough slow connections the bridge becomes unresponsive. Since the bridge is on `0.0.0.0` (Finding 1), any LAN host can execute this without authentication.

**Recommended fix:**
```go
s.httpServer = &amp;http.Server{
    Handler:           mux,
    ReadHeaderTimeout: 5 * time.Second,
    ReadTimeout:       10 * time.Second,
}
```

### FINDING 4 — No rate limiting or connection cap on auth attempts (MEDIUM)

**File:line:** `bridge/internal/ws/handler.go:49-52`, `bridge/internal/ws/server.go:39`

```go
if !validateBearer(r, token) {
    http.Error(w, "Unauthorized", http.StatusUnauthorized)
    return
}
```

**Severity:** Medium

**Attack scenario:** Any LAN host can make unlimited HTTP requests to `/ws` with arbitrary tokens. There is no per-IP throttle, no lockout after N failures, and no maximum connection count. Combined with the 43-character base64url token space (256-bit), brute force is computationally infeasible, but the absence of any rate limiting means the timing oracle in Finding 2 becomes more tractable, and the server is open to the Slowloris variation in Finding 3.

**Recommended fix:** Add a `ReadHeaderTimeout` (fixes the Slowloris angle), and optionally a per-IP rate limiter using `golang.org/x/time/rate` (already transitively available via the Tailscale dependency). Log repeated auth failures.

### FINDING 5 — Origin check disabled; browser-based CSRF possible if token is leaked (LOW-MEDIUM)

**File:line:** `bridge/internal/ws/handler.go:54-56`

```go
conn, err := websocket.Accept(w, r, &amp;websocket.AcceptOptions{
    InsecureSkipVerify: true, // LAN only; origins vary
})
```

**Severity:** Low-Medium

**Attack scenario:** `InsecureSkipVerify: true` disables the `coder/websocket` library's `Origin` header enforcement. The library's comment explicitly warns this opens the server to CSRF attacks. Concretely: if a malicious web page is open in a browser on the same Mac (or any LAN host with a browser), it can use the browser's `WebSocket` API to connect to `ws://192.168.x.x:47821/ws?token=TOKEN` from a cross-origin page — but only if it already has the token. The threat is real if the token is ever visible in browser history (e.g., if the user visits a URL that includes the token, or if the token is copied into a browser address bar). Combined with Finding 1 (cleartext), a LAN attacker who sniffed the token could then embed a WebSocket connection in a page served to the victim's browser.

**Recommended fix:** Replace `InsecureSkipVerify: true` with an explicit `OriginPatterns` allowlist of the iOS app's custom scheme, or require the `Authorization` header only (which browser `WebSocket` API cannot set, unlike query params). At a minimum, reject connections that provide the token via `?token=` query param from a browser Origin that doesn't match the host.

### FINDING 6 — cmux socket password stored plaintext in config.json (LOW)

**File:line:** `bridge/cmd/cmux-bridge/main.go:76-84`, `bridge/internal/pair/qr.go` (prompt)

```go
// config.json (0600) at ~/.config/cmux-bridge/config.json:
```

**Severity:** Low

**Attack scenario:** The cmux socket password is stored as plaintext JSON in `~/.config/cmux-bridge/config.json`. The file permissions are `0600` (correct). **Recommended fix:** Store the password in the macOS Keychain via `security add-generic-password` rather than a plaintext config file. The bridge then stored and sends `\u001b` as the socket password. Consider switching to `term.ReadPassword` (which suppresses echo and handles escape properly) and explicitly rejecting non-printable characters.

### FINDING 7 — Unbounded Unix socket response line read (LOW)

**File:line:** `bridge/internal/socket/client.go:102`

```go
line, err := c.reader.ReadString('\n')
```

**Severity:** Low

**Attack scenario:** `bufio.NewReader` with default 4096-byte internal buffer calls `ReadString('\n')`, which grows without bound until a newline is found or an error occurs. If the cmux Unix socket returns a response with no newline (e.g., a very large JSON object, a corrupted response, or a compromised cmux process), this allocates unbounded memory in the bridge process. The 10-second deadline on the connection (`SetDeadline`) bounds the time window but not the allocation size within that window. This is only exploitable by a compromised or malicious cmux process (local threat), not by a remote WebSocket client (the method and params are JSON-serialized by the bridge before sending, so remote clients cannot inject raw newlines into the socket stream — verified: Go's `json.Marshal` escapes `\n` as `\u000a`/`\\n`).

**Recommended fix:** Use `bufio.NewReaderSize(conn, 4*1024*1024)` with a size cap, or read into an `io.LimitedReader` before parsing. Since the cmux socket is trusted-local, this is low severity.

### 1. DATA RACE — `cmuxConnectedFlag` read from WS goroutine, written from reconnect goroutine (CRITICAL)

**File:** `cmd/cmux-bridge/main.go`, lines 208, 232, 233, 252, 266, 322

```go
// main.go:208 — declared on the stack, no synchronization
cmuxConnectedFlag := false

// main.go:220 — goroutine A: reconnect loop writes it
go func() {
    ...
    cmuxConnectedFlag = false   // line 233, 266
    cmuxConnectedFlag = true    // line 252
}()

// main.go:322 — goroutine B: every new WS connection reads it via closure
server := ws.NewServer(token, poll, cmuxClient, func() bool { return cmuxConnectedFlag })
```

The closure `func() bool { return cmuxConnectedFlag }` is called from `handleClient` (line 70 of handler.go) in each HTTP handler goroutine spawned by `net/http.Server.Serve`. That is a concurrent read from a goroutine that did not write it. Meanwhile the reconnect goroutine writes it without any lock. This is a textbook data race on a plain `bool` variable.

**Scenario:** iOS client connects → `handleClient` reads `cmuxConnectedFlag` via closure → simultaneously the reconnect goroutine writes `cmuxConnectedFlag = true`. The Go memory model gives no guarantee; the race detector will flag it.

**Fix:** Replace `cmuxConnectedFlag bool` with `var cmuxConnected atomic.Bool` (from `sync/atomic`) and use `.Store(true/false)` / `.Load()`. The closure becomes `func() bool { return cmuxConnected.Load() }`.

### 2. DEADLOCK WINDOW — `Send` holds mutex while blocking on network I/O, so `Connect` called by the reconnect loop starves until the 10 s deadline fires (MEDIUM)

**File:** `socket/client.go`, lines 74–128

```go
func (c *Client) Send(...) (json.RawMessage, error) {
    c.mu.Lock()
    defer c.mu.Unlock()
    ...
    _ = c.conn.SetDeadline(time.Now().Add(10 * time.Second))
    // blocks up to 10s holding the lock:
    line, err := c.reader.ReadString('\n')
    ...
}
```

`Connect` also acquires `c.mu`. If the poller calls `Send("notification.list")` (1-second tick) and the cmux socket hangs (e.g., under a slow scrollback read returning lots of data), the mutex is held for up to 10 seconds. During those 10 s, the reconnect goroutine's `cmuxClient.Connect()` is blocked waiting for the same mutex — and the ping goroutine's `cmuxClient.Send("system.ping")` is also blocked. This is not a true deadlock (it resolves when the deadline fires), but it causes a 10 s head-of-line stall on all socket callers and can mask connection loss for up to `(10s send timeout) + (5s ping interval)`.

**Severity note:** For the stated concern about "10 s deadline behavior on slow big scrollback reads" — this is the mechanism. If `surface.read_text` returns a large payload, the `ReadString('\n')` call holds the mutex for up to 10 seconds, serializing every other caller. The poller will miss ticks and the ping loop will appear frozen.

**Fix:** Separate the read path from the mutex or switch to a non-blocking pipeline (one goroutine owns the conn and processes request/response pairs via a queue). The simplest safe fix that preserves the serial design: keep the mutex but increase the deadline or make it configurable per-method. A more complete fix uses a request channel + dedicated reader goroutine.

### 3. LOGIC BUG / NOTIFICATION DUPLICATION — `ResetSeenIDs` race with in-flight `poll()` (LOW-MEDIUM)

**File:** `poller/poller.go`, lines 106–148; `ws/handler.go`, lines 139–140

The flow is:
1. iOS sends `notification.clear` → `proxyCommand` calls `client.Send("notification.clear")` (holds `socket.Client.mu`, sends to cmux, gets ack).
2. After `Send` returns, `poll.ResetSeenIDs()` is called (acquires `poller.mu`, replaces `seenIDs` with a new empty map).
3. Meanwhile, the poller goroutine could have called `client.Send("notification.list")` before step 1 (it was blocked on the socket mutex), got a result back, and is now sitting at `p.mu.Lock()` in `poll()` ready to populate the new empty `seenIDs` with stale pre-clear notification IDs.

**Scenario:** Poller calls `notification.list`, blocked waiting for socket mutex (which WS handler holds for `notification.clear`). WS handler completes, calls `ResetSeenIDs()` (empties the map). Now the poller acquires `poller.mu` and adds all the old IDs back from its stale `notification.list` response into `seenIDs`, silently suppressing the "re-emit after clear" behavior the code intends.

**Fix:** The simplest fix is a generation counter in the poller: `ResetSeenIDs` increments the generation; `poll()` records the generation before calling `Send` and discards the result if the generation changed during the RPC call.

### 10. LOW — Bearer token comparison is not constant-time

**File:** `bridge/internal/ws/auth.go:21`
```go
return provided == token &amp;&amp; provided != ""
```
Plain string `==` is susceptible to timing side channels. On a local LAN this is low-severity (an attacker would need LAN access to probe timing), but it's easy to fix.
**Fix:** Replace with `subtle.ConstantTimeCompare([]byte(provided), []byte(token)) == 1` from `crypto/subtle`.
